# `prisma` — schema and migration conventions

The schema is **derived from the domain**. Model the aggregate and its invariants first, then write
the migration that stores it.

## Naming

Prisma models are `PascalCase` and singular (`User`, `Session`, `Streak`); tables and columns are
`snake_case` through `@@map` / `@map`; every table is prefixed by its owning context
(`identity_users`, `gamification_streaks`, `open_finance_consents`) so ownership is visible in
`psql`. Postgres enums are mapped too (`identity_registration_consent_scope`).

## Hard rules

- **No foreign key crosses a context.** `gamification_streaks.user_id` is a bare `uuid`, and so is
  every `sandbox_bank_*.customer_id`. Relations exist only inside one context — identity's
  sessions, gamification's badges, `open_finance_*` hanging off `open_finance_consents`, and
  `sandbox_bank_ledger_entries → sandbox_bank_accounts`.
- **`sandbox_bank_*` belongs to a foreign system** that happens to share the database. No query
  outside `src/modules/sandbox-bank/infrastructure` touches those tables — not even a read model.
- Timestamps are `Timestamptz(3)`. Money is integer cents (`Int`, `BigInt` past 21M BRL) — `Float`
  on a monetary column is a review blocker. No monetary column exists yet.
- Ids are `@db.Uuid`, generated by the application (UUID v7), never by the database: an aggregate is
  valid before it is persisted.
- A nullable column is a claim that the domain allows absence, and each one says so in a `///`
  comment on the model (`revoked_at` while usable, `last_synced_at` until the first sync, a sandbox
  consent's `customer_id` until somebody authorises it).
- Secrets are never stored in clear. Bank tokens and the PKCE verifier are AES-256-GCM ciphertext
  (`*_ciphertext`, prefixed `v1.`); codes, tokens and `state` the platform only has to *match* are
  SHA-256 fingerprints (`*_fingerprint`).
- `version` columns on `gamification_streaks` and `gamification_badge_collections` exist for
  optimistic locking when those aggregates start being updated by concurrent requests.
- No triggers, no stored procedures, no computed business columns. `DEFAULT` and `CHECK` guarding a
  data invariant are the exception.

## Migrations

```bash
npx prisma migrate dev --name <slug>     # generates, applies, regenerates the client
npx prisma migrate deploy                # applies pending migrations (CI, test database)
```

Never hand-edit an applied migration, and never `db push` against a shared database.

**CHECK constraints are written by hand**, because Prisma cannot express them. They go in their own
migration folder with a `migration.sql` written directly — Prisma does not track them, so they cause
no drift. See `20261005024300_domain_check_constraints`, which enforces in the database what the
aggregates enforce in memory:

| Constraint                                       | The invariant it mirrors                       |
| ------------------------------------------------ | ---------------------------------------------- |
| `gamification_streaks_current_days_not_negative` | a streak counts days already lived through     |
| `gamification_streaks_longest_days_covers_current` | the longest streak is never shorter than the current one |
| `identity_users_email_is_normalised`             | `Email` is stored trimmed and lower cased      |
| `identity_users_display_name_within_bounds`      | `DisplayName` is 2 to 80 characters            |
| `identity_sessions_expires_after_issue`          | a session cannot expire before it was issued   |

`20261012170100_sandbox_bank_check_constraints` adds the consent flow's:

| Constraint                                                  | The invariant it mirrors                         |
| ----------------------------------------------------------- | ------------------------------------------------ |
| `sandbox_bank_ledger_entries_amount_not_zero`               | `LedgerEntry`: a movement of nothing is not one  |
| `sandbox_bank_ledger_entries_mcc_within_range`              | an MCC is a four-digit code                      |
| `sandbox_bank_consents_expires_after_creation`              | a consent cannot lapse before it exists          |
| `sandbox_bank_consents_authorised_names_its_accounts`       | an authorised consent names a customer and shares at least one account |
| `open_finance_authorisation_requests_expires_after_creation` | an OAuth round trip cannot expire before it opens |

`20261017224927_gamification_goals_check_constraints` adds the goals':

| Constraint                                              | The invariant it mirrors                          |
| ------------------------------------------------------- | ------------------------------------------------- |
| `gamification_savings_goals_title_within_bounds`        | `GoalTitle`: trimmed, 3 to 60 characters          |
| `gamification_savings_goals_target_within_bounds`       | `GoalAmount`: positive, at most R$ 10.000.000,00  |
| `gamification_goal_movements_amount_within_bounds`      | a movement of nothing is not one                  |
| `gamification_ceiling_terms_amount_within_bounds`       | `CeilingAmount`: zero allowed, never negative     |
| `gamification_ceiling_terms_destination_not_blank`      | `CeilingDestination`: absent or trimmed words     |
| `gamification_ceiling_terms_effective_from_is_a_month`  | `effective_from` is a `YYYY-MM` key               |

`gamification_savings_goals.version` and `gamification_betting_ceilings.version` are live optimistic
locks: the repository updates `WHERE version = n` and a lost race surfaces as `409`.

**External ids** (`open_finance_*.external_id`, `external_consent_id`) were added NOT NULL by
add → backfill → require in one migration: rows that predate the flow were never fetched from a
DataHolder, so their own id is the only external id they have.

Index every foreign key and every column a repository filters or sorts by, in the same migration as
the repository method. `open_finance_consents` is indexed on `(user_id, status)` because the only
question asked of it is "has this user an authorised consent".

## Seeding

`seed.ts` holds **synthetic data only**. No real CPF, CNPJ, name, address or bank movement ever
enters this repository. It creates one demo user (`ana@exemplo.com`), books a synthetic year at
`sandbox-bank`, and then connects that user through the real consent flow over HTTP against a
copy of the API on a spare port — so nothing in `open-finance` is written past its own rules.
`--without-consent` stops after the bank.
